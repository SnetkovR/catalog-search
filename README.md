# Поиск фотографий в каталоге

Локальный поиск похожих изображений: **DINOv2 Small → NumPy → FastAPI**.
Инференс выполняется только на CPU. Платные API не используются.

[![Tests](https://github.com/SnetkovR/catalog-search/actions/workflows/tests.yml/badge.svg?branch=main)](https://github.com/SnetkovR/catalog-search/actions/workflows/tests.yml)

## Запуск

Требуется Python 3.12 и [uv](https://docs.astral.sh/uv/). На Linux устанавливается
CPU-сборка PyTorch. На macOS устройство также явно зафиксировано как CPU;
CUDA и MPS не используются.

```sh
uv sync --locked
uv run catalog-search serve
```

Откройте **http://127.0.0.1:8000**. Документация API: **http://127.0.0.1:8000/docs**.

В уже подготовленном окружении этого проекта можно обойтись без `uv` в PATH:

```sh
.venv/bin/catalog-search --offline serve
```

Каталог по умолчанию: `data/catalog`. JPEG, PNG и WebP читаются рекурсивно.
Пользовательские фотографии, веса, скриншоты и индекс исключены из Git.

Модель и зависимости скачиваются при первоначальной настройке. Для скачивания
весов запускайте сервер или первую индексацию **без** `--offline`. Далее этот флаг запрещает
сетевые обращения за моделью. Индекс хранится в `var/catalog.sqlite3`, веса —
в `.cache/huggingface`.

## Запуск в Docker

Из корня репозитория:

```sh
docker compose up --build -d
docker compose logs -f catalog-search
```

Откройте **http://localhost:8000**. Сервер внутри контейнера слушает `0.0.0.0:8000`,
Compose публикует порт **8000 контейнера на 8000 хоста**, в том числе для доступа
по адресу хоста из сети. Если порт занят локальным сервером, выберите другой:

```sh
CATALOG_PORT=8080 docker compose up --build -d
```

В этом случае интерфейс доступен на `http://localhost:8080`. Настройка использует
стандартное [сопоставление портов Compose](https://docs.docker.com/compose/how-tos/networking/).

- `./data/catalog` подключается в контейнер как `/app/data/catalog` только для чтения.
  Добавляйте фотографии в папку на хосте; фоновая задача увидит их без пересборки образа.
- Индекс и миниатюры сохраняются в Docker volume `catalog-index`, веса — в `model-cache`.
  Эти volumes независимы от локальных `var` и `.cache` и переживают пересоздание контейнера.
- Фотографии, локальный индекс, веса и окружение Python исключены из build context
  через `.dockerignore` и не попадают в образ. В образ устанавливаются только runtime-зависимости.
- При первом запуске контейнер скачает модель, затем автоматически проиндексирует каталог.
  Пока загружается модель, HTTP-сервер еще не готов. GPU не требуется.

Полезные команды:

```sh
docker compose ps
docker compose exec catalog-search catalog-search status
docker compose restart catalog-search
docker compose down
```

`docker compose down` сохраняет данные volumes. Для повторного запуска без обращений
за уже скачанной моделью: `HF_HUB_OFFLINE=1 docker compose up -d`.
Чтобы перестроить индекс при смене модели/подготовки, остановите сервис перед CLI-командой:

```sh
docker compose stop catalog-search
docker compose run --rm catalog-search --offline index --rebuild
docker compose up -d
```

## Фоновая индексация

Команда `serve` автоматически запускает одну фоновую задачу. Первый проход начинается
сразу после загрузки модели; каждый следующий — **через 60 секунд после завершения
предыдущего**. При длительной индексации новые проходы не накладываются друг на друга.
Добавление, изменение и удаление файлов больше не требуют ручного запуска `index`.

Задача использует ту же модель в памяти, что и поиск. Поисковые запросы имеют приоритет
между пакетами индексации; уже начатый пакет завершается перед обработкой запроса.
Чтение каталога и миниатюр остается доступным. Файловая блокировка предотвращает
одновременную запись этой задачей и отдельной CLI-командой `index`.

Новые или измененные менее 2 секунд назад файлы откладываются до следующей проверки.
Если размер, время изменения или inode поменялись во время чтения, файл также
откладывается, а его прежняя запись сохраняется. При длительном копировании надежнее
писать во временный файл без расширения изображения и переименовывать после завершения.

Состояние задачи и ошибки видны в UI и в поле `indexing` ответа `GET /api/status`.
Страница проверяет состояние каждые 3 секунды и обновляет счетчик и карточки автоматически.
Текущая поисковая выдача при этом сохраняется; для новой выдачи повторите поиск.

```sh
# Настроить интервал и размер пакета
uv run catalog-search --offline serve --index-interval 60 --index-batch-size 4

# Отключить задачу и обновлять каталог только через CLI
uv run catalog-search --offline serve --index-interval 0
```

После ошибки задача повторяет попытку через минуту. При остановке сервера текущий
проход отменяется после завершения активного пакета. Готовые пакеты сохраняются
в SQLite для повторного запуска, опубликованный индекс остается прежним.
Состояние задачи хранится в памяти; при новом запуске начинается новая проверка
с опорой на сохраненный индекс. Для фоновой работы сервер должен оставаться запущенным.

## Возможности

- Загрузка файла или перетаскивание в веб-интерфейс.
- Выделение области мышью/касанием или ввод координат с клавиатуры.
- Выдача ближайших изображений с косинусным сходством.
- Поиск аналогов прямо из каталога по сохраненному вектору, без повторного инференса.
- Исключение всех побайтово одинаковых копий запроса по SHA-256.
- Инкрементальная индексация, удаление устаревших записей, отчет о поврежденных файлах.
- Автоматическая проверка изменений раз в минуту и обновление карточек в интерфейсе.
- Локальная обработка загрузок: файл не добавляется в каталог; временный файл
  multipart-загрузки закрывается после чтения.

Веб-интерфейс показывает по 24 карточки каталога; остальные доступны по кнопке
«Показать ещё». Для поиска по снимку из каталога сам снимок и его точные копии
исключаются всегда. Для загрузки файла это настраивается флажком.

## Команды

Общие опции (`--catalog`, `--storage`, `--threads`, `--offline`, `--model-cache`)
указываются **перед** названием команды.

```sh
# Первое построение или обновление после изменения файлов
uv run catalog-search --threads 4 index --batch-size 4

# Поиск без самого файла и его точных копий
uv run catalog-search --offline search 'data/catalog/2026-09-26 15.11.52.jpg' \
  --top-k 3 --exclude-identical

# Область: слева, сверху, справа, снизу — координаты от 0 до 1
uv run catalog-search --offline search query.jpg --crop 0.1 0.05 0.9 0.6

# Другая папка и отдельный индекс
uv run catalog-search --catalog /path/to/photos --storage var/other index
uv run catalog-search --catalog /path/to/photos --storage var/other --offline serve --port 8001

# Состояние индекса без загрузки модели
uv run catalog-search status

# Полная перестройка после изменения модели или подготовки фотографий
uv run catalog-search --offline index --rebuild

# Замеры и top-3 для каждой фотографии с исключением точных копий
uv run catalog-search --offline benchmark --limit 20 --repeats 3 \
  --output var/benchmark.json
```

Повторная индексация сначала сравнивает размер, mtime, ctime, inode и устройство.
Файлы с неизменными метаданными не перечитываются. Раз в сутки выполняется полная
сверка SHA-256, которая обнаруживает изменения даже при совпадающих метаданных.
Принудительная сверка: `catalog-search index --verify`; период на сервере задается
через `serve --index-verify-interval 86400` (0 — сверять каждый проход).
Отчёт содержит `fast_skipped`, `hashed` и `full_verification`. Проход без изменения
содержимого сохраняет поколение индекса и загруженную матрицу векторов. Поврежденные и слишком большие
файлы пропускаются с отчетом; если файл испортился, его старая запись удаляется.
Вложенные символические ссылки за пределы каталога не индексируются.

Эмбеддинги и миниатюры публикуются одной SQLite-транзакцией. Каждый готовый пакет
до публикации сохраняется в промежуточных таблицах; сбой или остановка сервера
не уничтожают выполненную работу. Следующий проход сверяет SHA-256 файлов и
переиспользует готовые эмбеддинги (`resumed` в отчете). Измененные файлы пересчитываются,
удаленные не публикуются. Смена модели, каталога или режима `--rebuild` сбрасывает
несовместимые промежуточные результаты. Для продолжения rebuild повторите `index --rebuild`.
Незавершенный пакет вычисляется заново. После успешной публикации промежуточные
таблицы очищаются; поиск подхватывает новую версию при следующем запросе.
Файлы повторно проверяются после инференса: изменившиеся откладываются. При rebuild
нестабильные файлы отменяют публикацию всего прохода, сохраняя предыдущий индекс.

## Устройство проекта

### Схема SQLite и резервные копии

Формат БД версионируется через `PRAGMA user_version`. При первой записи старая схема
мигрирует автоматически, без пересчета эмбеддингов. Перед миграцией создается копия
`var/catalog.before-v2-*.sqlite3`. Неизвестная будущая версия отклоняется.

```sh
# Можно выполнять при работающем сервере: копия включает закоммиченные WAL-страницы.
uv run catalog-search backup var/backups/catalog.sqlite3

# Сначала остановите сервер, затем восстановите проверенную копию.
uv run catalog-search restore var/backups/catalog.sqlite3
```

Копия проверяется на целостность SQLite и корректность эмбеддингов. Существующий файл
backup не перезаписывается. Восстановление требует той же папки каталога и блокируется,
пока сервер или индексатор используют хранилище. Прежние файлы БД сохраняются в
`var/before-restore-*`, включая поврежденную БД. Фотографии и веса нужно копировать отдельно.
После восстановления очередной проход сверит индекс с актуальными фотографиями.

Для Docker команды выполняются с теми же volumes: `docker compose exec catalog-search
catalog-search backup /app/var/backups/catalog.sqlite3`; перед `restore` остановите сервис
и используйте `docker compose run --rm catalog-search restore /app/var/backups/catalog.sqlite3`.

```text
src/catalog_search/
  config.py       Пути, лимиты, фиксированная ревизия модели
  images.py       Декодирование, EXIF, область поиска, подготовка и миниатюры
  encoder.py      DINOv2 Small, FP32, CPU, нормализованный CLS-вектор
  catalog.py      SQLite и точный поиск скалярным произведением в NumPy
  cli.py          Команды index/search/status/serve/benchmark
  api.py          FastAPI, лимиты загрузок и управление параллельными запросами
  jobs.py         Фоновая индексация, приоритет поиска, остановка и состояние задачи
  benchmark.py    Замеры и примеры выдачи
  static/         Веб-интерфейс без сборки и внешних ресурсов
tests/            Проверки индекса, изображений, API и браузерных сценариев
```

Вектор имеет 384 компоненты FP32: для 100 000 снимков сама матрица занимает
около 154 МБ. Метаданные, копии при загрузке индекса, модель и миниатюры требуют
дополнительной памяти. Скорость на больших каталогах пока не измерялась.

Вместо первоначально запланированного FAISS применяется NumPy: установленные
macOS-сборки FAISS и PyTorch конфликтовали из-за OpenMP. Поиск остается точным,
по косинусному сходству, без приближений.

## Проверки

```sh
uv run pytest -q
uv run ruff check src tests
uv run ruff format --check src tests

# Дополнительные проверки в headless Chromium
PLAYWRIGHT_BROWSERS_PATH=.cache/ms-playwright uv run playwright install chromium --only-shell
RUN_BROWSER_TESTS=1 PLAYWRIGHT_BROWSERS_PATH=.cache/ms-playwright \
  uv run pytest tests/test_browser.py -q
```

Обычные тесты используют небольшой детерминированный энкодер и не скачивают веса.
Браузерные тесты по умолчанию пропускаются. Реальная модель проверяется командой
`benchmark` и загрузкой фотографии через интерфейс. Первые замеры и наблюдения:
[docs/initial-evaluation.md](docs/initial-evaluation.md).

## GitHub Actions

Workflow [Tests](.github/workflows/tests.yml) запускается при каждом push, при
открытии и обновлении pull request, а также вручную через **Actions → Tests → Run workflow**.

Проверки выполняются на Ubuntu 24.04 в трех параллельных задачах:

- **Python 3.12**: Ruff, проверка форматирования и все тесты, кроме браузерных.
- **Python 3.13**: тесты обработки изображений, каталога, API и фоновой индексации.
- **Browser tests (Chromium)**: загрузка, выделение области, мобильная верстка
  и обновление каталога в фоне. Chromium устанавливается вместе с системными зависимостями.

Зависимости устанавливаются строго из `uv.lock`, кеш uv переиспользуется между
запусками. Тесты используют временные синтетические данные и тестовый энкодер;
`HF_HUB_OFFLINE=1` исключает скачивание модели. Секреты и фотографии пользователя
для запуска не нужны.

JUnit XML-отчеты сохраняются в артефактах запуска на 7 дней, в том числе при
падении тестов. Более новый запуск для той же ветки или PR отменяет предыдущий.
Посмотреть результаты: [GitHub Actions](https://github.com/SnetkovR/catalog-search/actions/workflows/tests.yml).

## Границы первой версии

- Это поиск визуально похожих изображений, не подтверждение точного артикула.
  Сходство не является вероятностью; порог «товар отсутствует» пока не калиброван.
- Полные кадры вписываются в квадрат 224×224 с полями. Накладные и фон могут
  влиять на выдачу. Выделение области применяется к запросу; каталог пока
  индексируется целиком. Автоматического выделения товара и OCR нет.
- Ограничения загрузки: 20 МБ и 30 мегапикселей. Область задается после учета EXIF.
- Сервер рассчитан на локальный запуск в одном процессе. Одновременно выполняется
  один поиск; дополнительные запросы получают 503 и могут быть повторены.
  Для публичного размещения отдельно нужны аутентификация и ограничения нагрузки.
- Фоновая индексация делит CPU с поиском; запрос может ждать окончания одного пакета.
  При отдельной ручной индексации CLI загружает свою модель. `--threads` задает потоки
  PyTorch, а не глобальный лимит всех библиотек процесса.
- ONNX, INT8, приближенный индекс и дообучение не включены в MVP.

Этапы реализации и рабочие предположения: [PLAN.md](PLAN.md).

Модель: [facebook/dinov2-small](https://huggingface.co/facebook/dinov2-small),
лицензия Apache 2.0. При первом использовании потребуется скачать веса;
после загрузки модель работает локально. Ревизия весов закреплена в `config.py`.
